# 性能建议评估与验收

基于源项目 `2efd9fc`、审核仓库 `b6d5fe4`。Pro 已确认此前三项 P2 修复有效，未发现新的 P1/P2。本轮独立评估四项性能建议，采用可以量化收益且不改变下载内容的改动。

## 采用的改动

| 项目 | 改动与兼容边界 | 验证 |
| --- | --- | --- |
| 状态写放大 | 图片集合继续使用 v2 快照；勾选、隐藏和配置写入小型元数据覆盖层。新标签、图片变更和清空仍保存完整快照。恢复时同时校验 collectionId 与递增版本，旧覆盖层不能覆盖新快照；写入失败保留脏状态并向调用者报告。 | 1000 张图片的勾选/隐藏/配置恢复；新标签首次保存；旧v2快照缺失/无效collectionId的升级恢复；清空后旧覆盖层拒绝；写入失败重试；完整快照保存途中发生新勾选与配置修改。 |
| 长 DOM 扫描 | img/background 循环约每 8 ms 让出一次任务，32 个节点检查一次预算。使用 MessageChannel，不依赖动画帧。异步响应保持消息通道开启；清空、停止自动采集后丢弃旧批次。DOM 查询、脚本提取和单个复杂节点仍可能耗时，未承诺严格的最大任务时长。 | 400 张图片的完整结果与中途取消反例；真实 1000/6000/12000 节点扫描，图片数量与基线一致。 |
| 虚拟行复用 | 修正画廊没有有限高度导致虚拟列表渲染全量行的问题；复用滚动区间重叠行，仅创建进入行。普通浏览只探测卡片附近图片；需要全局尺寸筛选/排序时仍保留全量探测。相同格式的信任度升级保存到后台，但不触发格式筛选重排。 | 2400 张图片初始 10 行，12 次滚动均复用所有重叠行；原高清筛选与失败缓存重试浏览器回归通过。普通网格显式按内容计算行高，避免定高容器内行高归零；窄屏筛选组换行，1200×850、390×844、1200×360 布局检查通过。 |
| ZIP 缓冲区寿命 | 分卷 Blob 构造后释放已复制的图片条目引用，不再等待整个浏览器下载周期。 | 等待中的成功/失败下载均释放条目，修改原缓冲区不改变 ZIP 内容；终态后释放 Blob URL；真实 Offscreen ZIP 内容和回退标记回归通过。 |

## 测量结果

命令：`node scripts/benchmark-performance.mjs <sample> verify`。需要 Playwright，可通过 `PIC_PLAYWRIGHT_MODULE` 指定已有模块。程序使用独立 Chromium 配置目录和本地 HTTP 图片夹具；结果在 `output/performance/`。

同机 Chromium 145.0.7632.6 的基线与最终样本如下，数值是测试夹具结果，不代表所有网站。扫描为三次中位数，勾选为七次中位数；长任务统计来自源页 PerformanceObserver。

| 指标 | 基线 | 优化后 |
| --- | ---: | ---: |
| 两标签合计 6000 条记录，每次单图勾选写入 JSON 字节数（Node 存储适配器） | 3,117,624 | 624 |
| 真实浏览器约 2.4 MB 状态，单图勾选响应 | 186.9 ms | 1.2 ms |
| 6000 DOM 节点扫描端到端 | 227.6 ms | 211.5 ms |
| 12000 DOM 节点扫描端到端 | 459.3 ms | 479.3 ms |
| 12000 节点三次扫描的源页长任务 | 150 / 152 / 142 ms | 本样本未观察到 ≥50 ms 长任务 |
| 2400 张图，初始已渲染行 | 600 | 10 |

分批扫描的目标是减少连续阻塞，不是宣称扫描总耗时必然减少。存储覆盖层仍随已选/隐藏 ID 数量增长；图片元数据本身更新仍保存全量快照。

## 不采纳的架构改造

- **立即迁移到每标签存储分片或 IndexedDB**：当前实测主要交互瓶颈已由元数据覆盖层解决。进一步迁移涉及旧数据迁移、接近配额时的临时副本和跨键故障恢复；当前没有证明剩余图片快照写入收益足以覆盖该风险。暂不实施，不作为本轮缺陷反复提出。
- **严格全局/单文件 ZIP 内存硬上限或全面流式 ZIP/OPFS 改造**：现有分卷阈值不是严格峰值上限，超大单图和多个并行任务仍可能占用较多内存。简单硬上限会拒绝此前能下载的大图；队列、流式格式和临时文件方案还需处理恢复、取消、错误归属及回退路径。当前只采用已验证的重复缓冲区释放，不声称已经有严格预算。没有具体失败案例或明确超大并发产品需求时，不将该架构改造列为本轮必改项。

以上是不采纳当前改造方案的工程取舍，不是将潜在风险标为已修复。如果发现可复现的数据丢失、错误成功状态或常规任务失败，应作为具体缺陷重新评估。

## 回归

244 项 Node 测试、55 个 JS/MJS 语法检查通过；原有 12 项与新增 8 项真实浏览器场景通过。性能脚本额外验证虚拟滚动和三种窗口尺寸。审计中不以测试数量代替行为证据。


## Pro 复核后的框选修复

Pro 固定审核 `a8d9afa` / 源 `c4166d9` 后确认其他性能改动有效，只复现一项 P2：虚拟模式下框选仅遍历已挂载卡片，矩形覆盖128条时命中40条。该审计运行27项通过检查及一个反例；部分生产函数片段在真实Chromium中运行，未加载完整扩展，不能与本项目端到端测试混为一谈。

修复后，虚拟框选按完整行数据、卡片尺寸、间距和画廊内边距计算相交记录；DOM仅负责显示当前挂载卡片的高亮。滚动时使用最后的指针位置更新矩形，松开时重新计算，拖回后离开矩形的记录退出命中集合。普通布局保留DOM命中方式。

除128条/40个DOM节点的独立回归及行间空隙、部分末行反例外，完整扩展中的真实鼠标操作覆盖：向下跨屏覆盖128条、反向覆盖128条、同一手势拖回缩小至8条、普通切换128条中的已选8条后剩120条。过程中仅挂载10或18行，没有重新挂载全部600行；高亮更新只遍历已挂载节点。
